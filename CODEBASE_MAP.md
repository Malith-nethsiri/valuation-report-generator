## File: `backend/app/main.py`

### Responsibility
Application factory: loads environment, initialises Sentry/logging, configures CORS and the full middleware stack, mounts all 13 domain routers, and manages startup/shutdown lifecycle including Redis, DB, and two background tasks.

### Depends On
- `stdlib`: `asyncio`, `logging`, `os`, `datetime`
- `fastapi`, `fastapi.middleware.cors`, `fastapi.exceptions`
- `sqlalchemy.exc.SQLAlchemyError`
- `dotenv.load_dotenv`
- `sentry_sdk` + `FastApiIntegration`, `SqlalchemyIntegration`, `LoggingIntegration`
- `app.models` — queries `TokenBlacklist` directly
- `app.database` — `SessionLocal`, `engine`
- `app.middleware.csrf_protection.CSRFMiddleware`
- `app.middleware.rate_limiting` — `RateLimitMiddleware`, `configure_rate_limits`, `cleanup_task`
- `app.middleware.security_headers.SecurityHeadersMiddleware`
- `app.services.redis_client` — `get_redis_client`, `close_redis_connection`
- `app.utils.error_responses` — `add_request_id_middleware`, `generic_exception_handler`, `sqlalchemy_exception_handler`, `validation_exception_handler`
- `app.routers` — all 13 domain routers

### Used By
- `uvicorn` (ASGI server) — consumes the `app` object
- Every HTTP client (all requests enter through the middleware stack registered here)

### Data Impact
Every inbound HTTP request passes through this file's middleware chain:
`CORSMiddleware → RateLimitMiddleware → CSRFMiddleware → SecurityHeadersMiddleware → request_id injection → router dispatch`
All startup/shutdown resource lifecycle (Redis pool, DB engine, background tasks) is controlled here.

### Risks / Observations
1. **SRP leak — direct DB query in factory**: `_cleanup_token_blacklist` uses a raw `SessionLocal()` and queries `TokenBlacklist` inline. This is CRUD logic that belongs in `crud/user_crud.py` or a dedicated cleanup service, not the app factory.
2. **Module-level side effects on import**: `load_dotenv`, Sentry `init`, and `logging.basicConfig` fire at import time — makes isolated unit testing harder and can cause surprising ordering issues.
3. **Auto-migration risk**: `alembic upgrade head` runs synchronously inside the async `startup_event`. A slow or failing migration blocks startup. In production, a failed migration correctly raises `RuntimeError`, but a partial migration would leave the DB in an inconsistent state.
4. **Background task has no cancellation path**: `_cleanup_token_blacklist` loops indefinitely with no `asyncio.CancelledError` handling. On shutdown, the 5-second `asyncio.wait` timeout will simply abandon it rather than cancel it cleanly.
5. **Middleware order is implicit and undocumented**: The comment "last added = outermost" is correct for Starlette, but the actual execution order (CORS outermost, SecurityHeaders innermost before route) has security implications and is fragile if a developer adds middleware without understanding this.
6. **`on_event` deprecation**: FastAPI deprecated `@app.on_event` in favour of lifespan context managers. Not a runtime risk today, but a migration debt.

### Refactor Needed?
**Partial.** The `_cleanup_token_blacklist` DB query should move to a CRUD or service layer. The auto-migration block could be extracted to a standalone `run_migrations()` helper. The `on_event` handlers should eventually be migrated to a lifespan context manager.

Status: ☑ Reviewed

## File: `backend/app/models.py`

### Responsibility
Defines the complete SQLAlchemy ORM schema: 9 table classes, 1 shared mixin (~132 columns), and 3 enums — the single source of truth for all database structure in the system.

### Depends On
- `sqlalchemy` — `Column`, `Integer`, `String`, `DateTime`, `Text`, `ForeignKey`, `JSON`, `Numeric`, `Boolean`, `UniqueConstraint`, `func`, `relationship`
- `app.database.Base` — declarative base for all models
- `stdlib`: `uuid`, `enum`

### Used By
- Every CRUD file (`crud/report_crud.py`, `crud/property_crud.py`, `crud/vehicle_crud.py`, `crud/user_crud.py`, `crud/building_helpers.py`)
- Every router that queries or modifies data
- `app.main.py` — queries `TokenBlacklist` directly in background task
- `app.database.py` — `Base` is imported here to create tables
- Alembic migrations — auto-generated from these model definitions

### Data Impact
All persistent data in the system flows through these models. Key data topology:
- `User` → owns `Report`, `Property`, `Vehicle` (cascade delete)
- `Report` (via `PropertyDataMixin`) → contains 132+ property columns directly (single-property use)
- `Report` ↔ `Property` via `ReportProperty` junction (multi-property use)
- `Report` ↔ `Vehicle` via `ReportVehicle` junction (vehicle/mixed use)
- `TokenBlacklist` stores revoked JWT JTIs for logout enforcement
- `AuditLog` records all sensitive actions with nullable user_id (preserved after user deletion)
- `Job` tracks async DOCX/PDF generation with progress metadata

### Risks / Observations
1. **Dual-purpose `Report` model**: For single-property reports, the 132 `PropertyDataMixin` columns on `Report` are used directly. For multi-property reports, those same columns are effectively unused and the data lives in linked `Property` records. This creates a silent semantic split — you can't tell from the schema alone which mode a report is in without checking `is_multi_property`.
2. **Missing unique constraint on junction tables**: `ReportProperty` has no `UniqueConstraint('report_id', 'property_id')`. Same for `ReportVehicle`. A property or vehicle can be added to the same report twice at the DB level.
3. **Soft-delete + unique constraint conflict on `Vehicle`**: `Vehicle` has `UniqueConstraint('user_id', 'registration_number')` but also `is_deleted = Boolean`. A soft-deleted vehicle blocks creating a new vehicle with the same registration number for the same user. The constraint does not exclude `is_deleted=True` rows.
4. **`Job.status` not DB-enforced**: `JobStatus` enum is defined in Python but the column is `String(20)` — no DB-level constraint. An invalid status string can be persisted without error.
5. **`Report.properties` and `Report.vehicles` sort in-memory**: These `@property` methods call `sorted()` on a Python list. If SQLAlchemy lazy-loads `property_associations` or `vehicle_associations` inside a loop, this becomes an N+1 query. Requires `joinedload` or `selectinload` at the query site to avoid.
6. **`PropertyDataMixin` migration trap**: Any new column added to the mixin must be manually reflected in Alembic as two separate `alter_table` operations (once for `reports`, once for `properties`). Easy to get wrong — migration generators won't automatically duplicate it.
7. **Heavy JSON column reliance**: `buildings`, `comparable_properties`, `valuation_buildings_data`, `features`, `tyres`, `electrical`, `lights`, `suspension`, `past_valuations`, and others are `JSON`. Schema is documented only in code comments, not enforced. Any JSON schema drift is invisible until runtime.
8. **`TokenBlacklist.user_id` is nullable**: Intentional (user may be deleted) but means you cannot always correlate a blacklisted token back to a user in the audit trail.
9. **`Job.report_id` uses SET NULL on cascade**: Deleting a report orphans its job record (report_id becomes NULL). The `result_url` file may still exist in storage but with no route back to the originating report.
10. **No `deleted_at` / soft-delete on `Report` or `Property`**: Only `Vehicle` has `is_deleted`. Reports use `status` field semantics. This inconsistency means delete operations for Reports are hard deletes — no recovery path.

### Refactor Needed?
**Partial.** The `PropertyDataMixin` architecture is sound but the missing junction-table unique constraints and the soft-delete/unique-constraint conflict on `Vehicle` are correctness bugs that need migration fixes. The in-memory sorting on `Report.properties`/`Report.vehicles` needs load strategy enforcement at CRUD level, not here.

Status: ☑ Reviewed

## File: `backend/app/database.py`

### Responsibility
Initialises the SQLAlchemy engine with a connection pool, creates the `SessionLocal` factory and `Base` declarative class, and provides the `get_db` FastAPI dependency that yields scoped DB sessions to route handlers.

### Depends On
- `sqlalchemy`: `create_engine`, `text`, `declarative_base`, `sessionmaker`, `OperationalError`, `DisconnectionError`
- `dotenv.load_dotenv`
- `stdlib`: `os`, `logging`, `pathlib.Path`

### Used By
- `app.models` — imports `Base` to define ORM models
- `app.main.py` — imports `SessionLocal` (background task), `engine` (shutdown dispose)
- All 13 routers — inject `get_db` via `Depends(get_db)`
- All CRUD files — receive the `db: Session` yielded by `get_db`

### Data Impact
Every DB read and write in the system passes through the `engine` and `SessionLocal` created here. The connection pool (`pool_size=10`, `max_overflow=20`, max 30 simultaneous connections) governs all database concurrency. Session lifecycle (commit/rollback/close) is managed by route handlers and CRUD callers via the yielded session.

### Risks / Observations
1. **Live DB connection on module import**: Lines 41-42 execute `SELECT 1` synchronously at import time. Importing any module that imports `database.py` (i.e., importing `models`, any router, or any CRUD file) triggers a real database connection attempt. This makes test isolation impossible without a live database or significant mocking.
2. **Broken retry logic in `get_db`**: The `DisconnectionError` handler closes the first session, creates a new one, and calls `yield db` inside the `except` block — a second yield in the same generator. FastAPI consumes exactly one yield from a dependency generator. The second yield is never consumed; the retry session is created but the route handler never receives it. **The retry logic is silently a no-op.**
3. **Duplicate `load_dotenv` call**: `database.py` calls `load_dotenv` independently; `main.py` also calls it at module level before imports. The load order is determined by Python's import system, not by explicit sequencing. This can produce subtle env-override ordering differences between production (uvicorn) and test runners.
4. **`logging.basicConfig` called twice**: Both `main.py` and `database.py` call `logging.basicConfig` at module level. In CPython, the second call is a no-op if handlers are already configured, but it creates confusion about where logging is actually set up.
5. **Pool configuration may be sub-optimal for Neon (serverless Postgres)**: Neon recommends `NullPool` or its own pgBouncer pooler URL for serverless deployments. Standard SQLAlchemy pooling (`pool_size=10`) on top of Neon's own pooler results in double-pooling and can exhaust Neon's connection limits under load.

### Refactor Needed?
**Yes (targeted).** The broken retry in `get_db` should be removed — it provides false safety. The startup connection test should be moved to the `startup_event` in `main.py` rather than firing at import time. The `load_dotenv` and `logging.basicConfig` calls should be removed (already handled by `main.py`). The pool settings should be validated against Neon's recommendations.

Status: ☑ Reviewed

## File: `backend/app/base_crud.py`

### Responsibility
Provides the generic `BaseCRUD` base class (create / get / list / update / delete) with built-in ownership enforcement, and a standalone `verify_ownership` helper — the shared CRUD contract that all 5 domain CRUD files extend.

### Depends On
- `sqlalchemy.orm.Session`
- `typing.Type`, `typing.Optional` — `Optional` is imported but **never used**
- `app.models` — imported but **never used** (model type is passed as a constructor parameter)
- `app.database.Base` — imported but **never used**
- `fastapi.HTTPException` — lazy-imported inside `verify_ownership` (twice)

### Used By
- `crud/report_crud.py`
- `crud/property_crud.py`
- `crud/vehicle_crud.py`
- `crud/user_crud.py`
- `crud/building_helpers.py`

### Data Impact
Every standard CRUD operation on user-owned resources flows through this class. The `get` method enforces ownership on every read; `update` and `delete` chain through `get`, so ownership is transitively enforced for all mutations. The `create` method commits immediately (single-record transaction per call).

### Risks / Observations
1. **Fail-open ownership check (security risk)**: `verify_ownership` checks `if hasattr(entity, 'user_id') and entity.user_id != user_id`. If a model does **not** have a `user_id` attribute, the ownership check is silently skipped and the entity is returned to any authenticated user. The safe default should be fail-closed (deny access if `user_id` is absent).
2. **Mass-assignment in `update`**: The update loop sets any attribute present in the `data` dict using `setattr`. If a caller passes a dict containing `id`, `user_id`, or other sensitive fields, they will be overwritten silently. Protection exists only at the Pydantic/router layer — not at the CRUD layer itself.
3. **`get_user_list` has no stable sort order**: `skip`/`limit` pagination without an `ORDER BY` is non-deterministic. Records can appear on multiple pages or be skipped entirely if rows are inserted/deleted between page requests.
4. **Lazy `HTTPException` import (twice, inside function body)**: `from fastapi import HTTPException` is imported on lines 12 and 15 inside `verify_ownership`. No circular import justifies this — it should be a top-level import.
5. **Three unused imports**: `Optional` (typing), `models` (app), and `Base` (database) are all imported but never referenced in this file. Dead imports that add false coupling signals when reading dependencies.
6. **`create` always commits immediately**: No support for batch or transactional multi-entity creates. Callers that need to create multiple related entities atomically cannot use this method without bypassing the base class.

### Refactor Needed?
**Yes (targeted).** The fail-open ownership check (Risk 1) is a security issue and should be inverted to fail-closed. The unused imports should be removed. The `update` method should not set `id` or `user_id` even if present in the dict. `get_user_list` needs a default `ORDER BY created_at DESC` for stable pagination.

Status: ☑ Reviewed

## File: `backend/app/auth.py`

### Responsibility
JWT creation/verification, bcrypt password hashing, password strength validation, and the two FastAPI authentication dependencies (`get_current_user`, `require_admin`) used by all protected routes.

### Depends On
- `python-jose`: `JWTError`, `jwt`
- `passlib.context.CryptContext` — bcrypt
- `fastapi`: `HTTPException`, `status`, `Depends`, `Request`, `Cookie`
- `fastapi.security.HTTPBearer`
- `sqlalchemy.orm.Session`
- `dotenv.load_dotenv` — called **again** at module level (3rd location after `main.py` and `database.py`)
- `app.crud` — `get_user_by_email`
- `app.models` — `User`, `TokenBlacklist`
- `app.database.get_db`

### Used By
- Every protected router — injects `Depends(get_current_user)`
- Admin-only routes — injects `Depends(require_admin)`
- `routers/auth.py` — uses `create_access_token`, `create_refresh_token`, `verify_refresh_token`, `authenticate_user`, `get_password_hash`, `validate_password_strength`

### Data Impact
- Reads `TokenBlacklist` on **every authenticated request** (DB query per request, no Redis cache)
- Reads `User` by email on every authentication check
- Writes nothing directly — token creation and blacklisting are handled by the auth router/CRUD

### Risks / Observations
1. **`verify_token()` does not check token type**: `verify_token` decodes any valid JWT without confirming `payload["type"] == "access"`. A valid refresh token could be accepted where an access token is expected, as long as it was signed with `SECRET_KEY`. `verify_refresh_token` correctly enforces `type == "refresh"` — but the inverse check is missing in `verify_token`.
2. **`datetime.utcnow()` deprecated**: Both `create_access_token` and `create_refresh_token` use `datetime.utcnow()`, which is deprecated since Python 3.12. Should use `datetime.now(timezone.utc)`.
3. **Refresh token secret falls back to access token secret**: `REFRESH_TOKEN_SECRET_KEY = os.getenv("REFRESH_TOKEN_SECRET_KEY", SECRET_KEY)`. If the env var is missing, both token types share the same key — negating the security isolation of having two keys.
4. **TokenBlacklist DB query on every request with no caching**: Every call to `get_current_user` hits the DB to check token revocation. Under load, this is one extra DB round-trip per API call. The Redis cache service exists in the project but is not used here.
5. **`get_current_user` silently skips blacklist check for tokens without JTI**: `if jti:` means any token issued before JTI was added (or with a manually crafted JWT) bypasses revocation checks entirely.
6. **Third `load_dotenv()` call at module level**: Creates the same env-override ordering ambiguity noted in `database.py`. All three files (`main.py`, `database.py`, `auth.py`) independently load env.
7. **`COMMON_PASSWORDS` list is small (40 entries)**: NIST SP 800-63B recommends checking against a list of at least 100,000 compromised passwords. The current list blocks the most obvious passwords but provides minimal real protection.
8. **Timing attack on authentication**: `authenticate_user` returns `None` immediately if user not found (no bcrypt), but takes bcrypt time if user exists with wrong password. An attacker can distinguish existence of an email by response timing.

### Refactor Needed?
**Yes (security-targeted).** Fix `verify_token` to enforce `type == "access"`. Replace `datetime.utcnow()` with `datetime.now(timezone.utc)`. Cache the blacklist check in Redis. Remove redundant `load_dotenv` call.

Status: ☑ Reviewed

## File: `backend/app/crud/report_crud.py`

### Responsibility
Report CRUD: create, read (single/filtered/paginated/admin), update (with optional row-locking), delete, duplicate, and report-property association reads.

### Depends On
- `sqlalchemy.orm.Session`, `sqlalchemy.orm.joinedload`
- `app.models`, `app.schemas`
- `crud/building_helpers.py` — `_normalize_and_validate_buildings`, `_duplicate_entity_data`

### Used By
- `crud/__init__.py` (re-exported)
- `crud/property_crud.py` — imports `get_report` for ownership checks
- `crud/vehicle_crud.py` — imports `get_report` for ownership checks
- `routers/reports.py`, `routers/properties.py`, `routers/vehicles.py`

### Data Impact
All Report table reads/writes. `get_report` with `eager_load_for_docx=True` loads the full report graph (User, Vehicle, all Properties via junction) in one query. `update_report` supports `SELECT FOR UPDATE` locking for concurrent DOCX generation. `get_user_reports_filtered` computes dashboard stats (total, this_month, completed, draft) inline.

### Risks / Observations
1. **Optional ownership (`user_id=None`) pattern**: `get_report`, `update_report`, `delete_report` all accept `user_id=None`, which silently bypasses ownership filtering. Correct use depends entirely on the router layer passing the right value.
2. **`duplicate_report` does not copy vehicle associations**: If a report has linked vehicles (`report.vehicle_associations`), they are not duplicated. Only `property_associations` are copied. Vehicle-linked reports will produce an incomplete duplicate silently.
3. **Dashboard stats run on filtered query, not total user reports**: `get_user_reports_filtered` computes `this_month_count`, `completed_count`, and `draft_count` on the already-filtered result set. If the user has applied a search filter, the stats reflect filtered data, not their full report history. This is likely a UX bug.
4. **`get_user_reports` has no `ORDER BY`**: Pagination without sort order is non-deterministic (same issue as `BaseCRUD.get_user_list`).

### Refactor Needed?
**Yes (targeted).** Fix `duplicate_report` to copy vehicle associations. Fix dashboard stats to always run on the unfiltered user query. Add `ORDER BY created_at DESC` to `get_user_reports`.

## Data Category Taxonomy

> **Added:** 2026-03-01
> **Purpose:** Classify every PropertyDataMixin / Report field into its data-collection stage.
> This taxonomy is authoritative — the source of truth is `backend/app/utils/field_categories.py`.

### Workflow Sequence

```
Stage 1                Stage 2              Stage 3            Stage 4
PAPER-BASED        →   INSPECTION-BASED  →  COMPUTED/       →  VALUATION
                                             DERIVED            JUDGMENT

[P:C] Client Docs
[P:O] Official Recs
```

### Category Definitions

| Tag | Category | Source |
|-----|----------|--------|
| `[P:C]` | Paper-Based · Client Documents | Survey plan, title deed, applicant info — provided by the client (in-person, digitally, or via email). Future: auto-filled by email-parsing AI agent. |
| `[P:O]` | Paper-Based · Official Records | Gazette publications, municipal registers, local-authority offices, rates-assessment notices — obtained from government sources. |
| `[I]`   | Inspection-Based | All physical observations, measurements, and condition assessments made during the on-site visit. |
| `[CD]`  | Computed / Derived | System-generated, AI-generated (Claude), or external-API results (Google Maps, Google Places). Not directly entered by the user. |
| `[VJ]`  | Valuation Judgment | Professional market analysis performed after inspection — comparable properties, rate per perch, final market value. |

### Field-to-Category Mapping (Summary)

#### [P:C] Paper-Based · Client Documents (~35 fields)
Applicant information (`applicant_*`), report context (`report_reference`, `report_date`, `valuation_type`, `valuation_purpose`, `request_type`, `submission_*`), survey plan fields (`lot_number`, `plan_number`, `plan_date`, `licensed_surveyor_name`, `survey_plan_scale`, `plan_reference_notes`), land extent from plan (`land_extent_acres`, `land_extent_roods`, `land_extent_perches`, `land_traditional_name`, `lots_data`), deed data (`has_deed_info`, `deeds`), legal boundaries from plan (`boundaries`), property village (`property_village`), property identification (`property_identification_type`).

#### [P:O] Paper-Based · Official Records (~22 fields)
Assessment records (`assessment_number`, `property_number`, `is_municipal_limit`), administrative divisions (`property_divisional_secretariat`, `property_district`, `property_province`, `grama_niladari_division`, `hathpaththuwa`, `korale`, `pradeshiya_sabha`, `ward_number`), all legal aspects (`ownership_type`, `street_lines_*`, `building_limits_status`, `local_authority_data`, `rent_act_effectiveness`, `title_search_conducted`, `pedigree_search_conducted`, `valuation_basis_note`, `property_encumbered`, `encumbrance_*`, `building_distance_from_road`, `building_plan_approved`, `building_plan_reference`, `building_approval_authority`, `building_within_limits`, `local_authority_rated`, `local_authority_tax_levy`).

#### [I] Inspection-Based (~40 fields)
Inspection metadata (`inspection_date`), access observations (`access_road_type`, `property_road_position`, `access_road_conditions`, `access_entry_mode`, `location_direction`, `access_starting_point_name`), physical boundary state (`physical_boundaries_types`, `physical_boundaries_description`, `boundary_types_per_direction`, `entrance_type`), land physical characteristics (19 fields: `land_shape`, `land_type`, `land_frontage_*`, `land_level`, `soil_type`, `water_table_depth`, `flood_risk`, `inundation_risk`, `earth_slip_risk`, `land_condition`, `land_condition_description`, `elevation_changes`, `drainage_pattern`, `vegetation_type`, `natural_features`), all `buildings` sub-fields (observed on-site), photographs (`property_photos`), all locality fields (17 fields: `distance_to_major_town_km`, `major_town_name`, `water_supply_type`, `telecommunication_types`, `internet_types`, `has_public_transport`, `public_transport_routes`, `public_transport_frequency`, `nearest_bus_stop_*`, `nearest_railway_*`, `area_type`, `development_level`, `predominant_building_type`, `is_tourist_area`, `tourist_attractions_nearby`, `has_electricity`, `has_multiple_lots`).

#### [CD] Computed / Derived (~20 fields)
AI narratives (`land_description_text`, `building_description_text`, `locality_description_text`), extent calculations (`land_extent_hectares`, `land_extent_square_meters`, `land_extent_formatted`), Google Maps data (`property_latitude`, `property_longitude`, `access_starting_point_latitude`, `access_starting_point_longitude`, `access_route_data`, `access_directions_text`, `access_distance_km`, `access_duration_minutes`, `location_map_image_data`, `access_road_classes_detected`), Google Places (`nearby_facilities`), summary text (`boundaries_summary_text`), certification auto-fills (`certification_text`, `certificate_identity_confirmed`, `certification_valuer_name`, `certification_valuer_designation`, `certification_date`), system metadata (`field_sources`, `uploaded_documents`, `property_identification_documents`, `report_type`, `status`, `is_multi_property`, `property_count`, `use_applicant_address_as_property`, `invoice_data`).

#### [VJ] Valuation Judgment (~15 fields)
Market analysis (`comparable_properties`, `land_market_analysis`), land valuation (`valuation_land_extent`, `valuation_rate_per_perch`, `valuation_total_land_value`), building valuations (`valuation_buildings_data`, `valuation_total_buildings_value`), add-ons (`valuation_addons`, `valuation_total_addons_value`), final values (`valuation_market_value`, `valuation_forced_sale_percentage`, `valuation_forced_sale_value`, `valuation_insurance_value`), overrides (`valuation_manual_overrides`), totals (`total_valuation_amount`).

```json
    "category": "paper_client",
    "timestamp": "2026-03-01T10:30:00Z",

    "source": "ocr",

  }

```

**Source values:** `"ocr"` | `"manual"` | `"api"` | `"computed"`

### Email-Agent Future Integration

`[P:C]` (Paper-Based · Client Documents) fields are intentionally designed to be injectable by a future email-parsing AI agent. The workflow is:

```
Client emails documents → AI agent extracts data → PATCH /api/reports/{id}
  with field_sources[field] = build_field_source_entry("ocr", field, confidence=0.95)
```

The `field_sources` schema already captures the `category` key so the email agent can tag fields as `"paper_client"` from day one without requiring any schema changes.
