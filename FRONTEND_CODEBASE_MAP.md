## File: `frontend/src/main.tsx`

### Responsibility
App entry point: mounts the React tree (StrictMode → ErrorBoundary → App) and conditionally initialises Sentry for production error/performance monitoring.

### Depends On
- `react`, `react-dom/client`
- `@sentry/react`
- `./App.tsx`
- `./components/ErrorBoundary.tsx`
- `./index.css`
- Vite env vars: `VITE_SENTRY_DSN`, `MODE`

### Used By
- Nothing imports this — consumed directly by Vite as the module entry point

### Data Impact
No data flows through this file. It is purely structural: wraps the tree and configures the global error/observability layer.

### Risks / Observations
1. **Shallow PII scrubbing** — `beforeSend` only strips the `Authorization` header; user emails or names in URL params are still forwarded to Sentry.
2. **No `tracesPropagationTargets`** — distributed tracing headers may be injected into unintended third-party requests (Google Maps, SendGrid, etc.).
3. **Non-null assertion on `getElementById('root')`** — silent crash if the root div is ever absent from `index.html`.
4. **`console.info` in production path** — log noise; no functional risk.

### Refactor Needed?
No — appropriately minimal for an entry point.

Status: ☑ Reviewed

### Responsibility
Defines the complete client-side route tree, composes the top-level context hierarchy (`BrowserRouter → AuthProvider → AppRoutes`), and performs a one-time legacy draft migration on mount.

### Depends On
- `react-router-dom` — `BrowserRouter`, `Routes`, `Route`, `Navigate`, `Link`
- `./contexts/AuthContext` — `AuthProvider`, `useAuth`
- `./components/ProtectedRoute`

- `./pages/TestComponents` (dev/test)
- `lucide-react` — icons used only inside inline `LandingPage`
- `./utils/migrateLegacyDrafts` — `clearLegacyDrafts`

### Used By
- `main.tsx` — renders `<App />` as root

### Data Impact
No data transformation. Routes auth state (`user`, `isLoading` from `AuthContext`) to redirect decisions. All page-level data flows originate downstream from the routes defined here.

### Risks / Observations
1. **SRP violation** — `LandingPage` (~100 lines JSX) and `LegacyFormPage` are inlined in `App.tsx`. Both belong in `pages/`.
2. **Unprotected test/legacy routes** — `/legacy` and `/test-components` are publicly accessible with no auth guard and no env check. Security risk in production.
3. **No lazy loading** — all 10+ pages are eagerly imported; inflates initial bundle.
4. **Raw full-screen spinner** — `isLoading` state shows a plain `div` spinner; no layout shell causes layout flash.
5. **`ReportEditRouter` as route element** — a component that performs its own routing logic nested inside a `<Route>`, adding an indirection layer.
6. **`clearLegacyDrafts()` fires on every mount** — not truly one-time; runs on HMR reloads and test resets.
7. **File at 298 lines** — inlined pages + full route table; will breach 600 LOC rule if admin routes are added.

### Refactor Needed?
Partial — extract `LandingPage` and `LegacyFormPage` to `pages/`, add `React.lazy` + `Suspense`, guard or remove test/legacy routes.

## File: `frontend/src/contexts/AuthContext.tsx`

### Responsibility
Global auth state provider: holds `user` + `isLoading`, exposes login/logout/register/OAuth/profile-update actions, and initialises the CSRF token on mount and after every auth event.

### Depends On
- `react` — `createContext`, `useContext`, `useState`, `useEffect`, `ReactNode`
- `../types` — `User`
- `../services/api` — `authApi`, `setAuthToken`, `clearAuthToken`, `initializeCSRF`
- `../utils/secureStorage` — `authTokenStorage`

### Used By
- `App.tsx` -> `AppRoutes` (reads `user`, `isLoading`)
- `components/ProtectedRoute.tsx`
- Any component or hook that calls `useAuth()`

### Data Impact
Single source of truth for authentication state. Sets/clears the `Authorization` header on the Axios instance via `setAuthToken`/`clearAuthToken`. Persists tokens and user data via `authTokenStorage` (AES-256 sessionStorage).

### Risks / Observations
1. **`updateUserProfile` accepts `any`** — `userData: any` bypasses type safety; should be `Partial<User>` or a typed `UserUpdate`.
2. **`initializeCSRF()` fire-and-forget on mount** — not awaited; race condition if the first POST fires before the CSRF cookie is set.
3. **Network error silently clears auth** — `getCurrentUser()` failure in `checkAuth` (including 503, timeout) calls `clearAll()` and logs the user out, even for transient errors.
4. **No token refresh flow** — 401 on any non-auth endpoint triggers an immediate hard redirect to `/login` via `window.location.href`; short-lived tokens cause silent logouts.

### Refactor Needed?
Partial — fix the `any` type, add retry/refresh path for 401s, guard `clearAll()` against transient network errors.

## File: `frontend/src/services/api/client.ts`

### Responsibility
Axios singleton with 5-minute timeout, automatic CSRF header injection on mutating requests, exponential-backoff retry for network/server errors, and centralised per-status-code error handling.

### Depends On
- `axios`, `AxiosError`, `AxiosRequestConfig`
- `../../utils/secureStorage` — `authTokenStorage`
- `../../config` — `API_URL`
- `../../utils/csrf` — `getCSRFToken`

### Used By
- Every `services/api/*.ts` module
- `contexts/AuthContext.tsx` — `setAuthToken`, `clearAuthToken`, `initializeCSRF`

### Data Impact
Every HTTP request in the application flows through this Axios instance. Injects `Authorization` bearer token and `X-CSRF-Token` headers. Manages retry state via config-object mutation.

### Risks / Observations
1. **5-minute timeout on all requests** — 300,000ms justified for uploads but causes 5-minute UI hangs on stalled simple GETs.
2. **`window.location.href` on 401** — hard navigation bypasses React Router, destroys unsaved form state, skips `useNavigationBlocker`.
3. **No token refresh** — 401 immediately clears credentials and redirects; a single transient error logs the user out.
4. **`const` in `switch` without block scope** — `const requestUrl` and `const token` inside `case 401` without braces; valid but a known lint footgun.
5. **`_retryCount` mutated on shared Axios config object** — hidden side effect.
6. **`responseData` typed as `any`** — all error response parsing loses type safety.
7. **`console.error/warn` in production path** — should route through Sentry or a structured logger.

### Refactor Needed?
Partial — add token refresh, scope timeout per request type, replace `window.location.href` with a router navigation callback.

Status: ☑ Reviewed

### `frontend/src/utils/secureStorage.ts`

**Responsibility:** AES-256 encrypted sessionStorage wrapper for sensitive token data. Prevents plain-text token exposure in browser storage.

**Public Interface:**
- `class SecureStorage` — `setItem(key, value, ttlMinutes?)`, `getItem(key)`, `getItemWithExpiry(key)`, `removeItem(key)`, `clear()`, `hasItem(key)`
- `authTokenStorage` — pre-configured `SecureStorage` instance for auth tokens
- `hasValidToken()` — convenience check for valid stored token

**Dependencies:** `crypto-js` (AES encryption), browser `sessionStorage`, `navigator`/`screen` for key derivation

**Used By:** `AuthContext.tsx` (token persistence), `client.ts` (token retrieval for headers)

**Data Impact:** All tokens stored encrypted. Key derived from `navigator.userAgent + screen.width + screen.height + navigator.language`. Sessions cleared on tab close (sessionStorage).

**Risks / Observations:**
- Encryption key derived from browser fingerprint — **not stable** across screen resize or system language change; tokens become silently unreadable
- `hasValidToken()` calls `getItemWithExpiry()` but tokens are stored via `setItem()` without TTL — expiry check always passes (logical gap)
- `crypto-js` is a community library with known audit concerns vs Web Crypto API
- Key derivation is synchronous and predictable — not truly secret on shared machines

**Refactor Needed:** Medium — key derivation strategy should use a server-issued nonce or session-bound value; `hasValidToken()` expiry logic mismatches storage pattern.

**Status:** ☑ Reviewed

## Pervasive Patterns — Medium Priority

### 5. Three Incompatible Form State Patterns

The codebase has three distinct approaches to form state in the same application:

| Pattern | Used In | Problem |
|---------|---------|---------|
| **RHF `useFormContext()`** | Vehicle step components (`VehicleBasicInfoStep`, etc.) | Clean, correct |
| **Prop-drilling** | `steps/` folder + `AdditionalDetailsStep` + `ApplicantAndPurposeStep` | Props typed `any`, no autocomplete |
| **Callback/data pattern** | Section components (`BoundaryInformationSection`, `LandValuesSection`, etc.) | Requires bridge components at step boundaries |

The "callback/data" sections require bridge wrappers (`PropertyLocationNewStep`, `PropertySearchStep`) with stale-init local state. A shared `useRHFToBridge` hook would eliminate this pattern.

### 6. `StepComponentProps` Uses `any` Throughout

`types/multiStepForm.ts` declares `StepComponentProps` with `register`, `errors`, `watch`, `setValue`, `control` all typed `any`. This propagates to every `steps/` component. These should be typed with RHF's own generic types (`UseFormRegister<FormData>`, `FieldErrors<FormData>`, etc.).

### 7. Stale-On-Mount Local State Bridge (3 files)

`PropertySearchStep`, `PropertyLocationNewStep`, and `steps/PropertyPlanStep` all use this pattern:
```ts
const [formData, setFormData] = useState<Partial<Report>>({});
React.useEffect(() => {
    const currentValues = getValues();
    setFormData(currentValues);
}, [getValues]); // fires ONCE on mount, then stale
```
If RHF values change externally (navigation back, auto-fill), local state is never updated. Should use `watch()` directly.

### 8. Widespread Unguarded `console.log`/`console.error`

Only `PropertySearchStep.tsx` correctly uses `if (import.meta.env.DEV)` guards. 15+ other components have bare `console.log` or `console.error` that fire in production. Notable offenders:
- `MultiStepForm.tsx` — 13 unguarded `console.log` calls in edit mode init
- `GooglePlacesAutocomplete.tsx`, `GoogleLoginButton.tsx`, `ReportEditRouter.tsx`, all building components

## Component-Level Issues — Lower Priority

### 9. Modal Components Without `React.createPortal`

Four modals render inline rather than into `document.body`:
- `DeleteConfirmDialog.tsx`
- `NavigationConfirmModal.tsx`
- `SaveProgressModal.tsx`
- `JobProgressModal.tsx`

`AddBankAccountModal` correctly uses `createPortal` (to avoid nested form DOM issues). The others risk z-index and clipping problems inside scrollable containers. All modal components should use `createPortal`.

### 10. Duplicate `toTitleCase` Implementation

`MultiSelectWithCustomInput.tsx` defines its own `toTitleCase` function inline — identical to the one in `utils/textFormatter.ts`. Violates "Never duplicate logic" rule.

### 11. Root-Level Shim Files

Three backward-compat re-export shim files exist:
- `components/BuildingDescriptionTab.tsx` (shims `building/BuildingDescriptionTab`)
- `components/AdditionalDetailsStep.tsx` AND `components/ApplicantAndPurposeStep.tsx` at root level — potentially duplicate with `steps/` versions

The root-level versions and their shims should be consolidated. Verify which importer paths are canonical and delete the redundant files.

### 12. Radio Button Double-Binding Bug

In `steps/AdditionalDetailsStep.tsx` (and root-level `AdditionalDetailsStep.tsx`), `request_type` radio buttons use both `register("request_type")` and an `onChange` that calls `setValue("request_type", value)`. This double-binds the field. Only `register` is needed.

### 13. Dead Props

Multiple components have props declared in their interface and destructured in the signature but never used:
- `steps/ApplicantPurposeStep.tsx` — `getValues`
- `steps/ExtentBoundariesStep.tsx` — `getValues`
- `GoogleLoginButton.tsx` — `onSuccess`, `loginWithGoogle`
- `JobProgressModal.tsx` — `isPolling`
- `SaveProgressModal.tsx` — `saveError` (declared but never rendered)
- `DatePicker.tsx` — `placeholder`
- `BuildingDescriptionTab.tsx` — `addFloor`, `addRoom`, `updateRoom`, `removeRoom`, `copyOccupierFromFirstBuilding`

### 14. `any` Type Usage

`any` appears in 30+ component files. Most frequently:
- `register`, `watch`, `setValue`, `errors` props in all `steps/` components
- `updateBuilding(id, field: string, value: any)` in building components
- `(formData as any).access_entry_mode` in step bridges
- All comparable property array transformations in `MultiStepForm`

Per CLAUDE.md, `any` should never be used without an explanatory comment. Where `any` exists due to RHF types, the solution is to properly type `StepComponentProps`.

### 15. MUI Isolated to Single Component

`@mui/material` (`TextField`, `Autocomplete`) is used **only** in `ManualAddressInput.tsx`. The entire rest of the codebase uses Tailwind CSS. This creates a heavy dependency (adds ~300KB to the bundle) for one component. `ManualAddressInput` should be rewritten with Tailwind + `AutocompleteInput` to eliminate the MUI dependency entirely.
